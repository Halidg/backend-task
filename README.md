# Backend модуль заметок

Решение тестового задания: контракт API, Prisma-схема, безопасный метод изменения заметки, структура модуля и ответы на архитектурные вопросы. Авторизация считается уже выполненной внешним слоем; `userId` берется только из проверенного контекста пользователя, а не из тела или параметров запроса.

## Структура

```text
prisma/
  schema.prisma              модели User и Note, связь и индекс ленты
src/notes/
  notes.service.ts           метод updateNote и прикладные ошибки
  notes.service.spec.ts      unit-тесты обновления и проверки владельца
```

В реальном NestJS-модуле рядом находились бы `notes.controller.ts`, DTO с `class-validator`, `notes.module.ts` и общий `PrismaService`. Контроллер отвечает за HTTP и валидацию формы запроса, сервис — за сценарий и правило доступа, Prisma — за атомарный запрос к PostgreSQL.

## API

Базовый путь: `/v1`. Все эндпоинты требуют авторизованного пользователя. Формат ошибки единообразен:

```json
{
  "error": {
    "code": "NOTE_NOT_FOUND",
    "message": "Note not found"
  }
}
```

Чужая и несуществующая заметка возвращают одинаковые `404`, чтобы API не раскрывал существование чужих идентификаторов. `401 Unauthorized` возвращает общий слой авторизации до вызова модуля заметок.

### Создать заметку

`POST /v1/notes`

Тело:

```json
{
  "title": "План на неделю",
  "content": "Подготовить отчет"
}
```

`title` обязателен, после удаления пробелов имеет длину `1..200`. `content` необязателен и может быть строкой либо `null`. `userId`, `id` и даты от клиента не принимаются.

Успешный ответ — `201 Created`:

```json
{
  "id": "9e33bdfd-d749-4b03-b0ac-a442c04d4399",
  "title": "План на неделю",
  "content": "Подготовить отчет",
  "createdAt": "2026-09-27T16:00:00.000Z",
  "updatedAt": "2026-09-27T16:00:00.000Z"
}
```

Ошибки: `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`.

### Получить список своих заметок

`GET /v1/notes?limit=20&cursor=<opaque_cursor>`

`limit` — от 1 до 100, по умолчанию 20. Сортировка стабильная: `createdAt DESC, id DESC`. `cursor` непрозрачно кодирует пару значений последней записи; это keyset pagination без дорогого большого `OFFSET`.

Успешный ответ — `200 OK`:

```json
{
  "items": [
    {
      "id": "9e33bdfd-d749-4b03-b0ac-a442c04d4399",
      "title": "План на неделю",
      "content": "Подготовить отчет",
      "createdAt": "2026-09-27T16:00:00.000Z",
      "updatedAt": "2026-09-27T16:00:00.000Z"
    }
  ],
  "nextCursor": null
}
```

Запрос к данным всегда содержит `where: { userId }`. Ошибки: `400 INVALID_CURSOR`, `401 UNAUTHORIZED`.

### Получить одну свою заметку

`GET /v1/notes/:noteId`

Успешный ответ — `200 OK` с объектом заметки в том же формате. Поиск выполняется сразу по `id` и `userId`.

Ошибки: `400 VALIDATION_ERROR` для некорректного UUID, `401 UNAUTHORIZED`, `404 NOTE_NOT_FOUND` для отсутствующей или чужой заметки.

### Изменить свою заметку

`PATCH /v1/notes/:noteId`

Тело содержит хотя бы одно разрешенное поле:

```json
{
  "title": "Новый заголовок",
  "content": null
}
```

`null` очищает `content`; отсутствие поля оставляет его без изменений. `title: null` запрещен. Лишние поля отклоняются HTTP-валидацией (`whitelist` + `forbidNonWhitelisted` в NestJS), а сервис дополнительно формирует объект обновления только из `title` и `content`.

Успешный ответ — `200 OK` с обновленной заметкой. Ошибки: `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `404 NOTE_NOT_FOUND` для отсутствующей или чужой заметки.

### Удалить свою заметку

`DELETE /v1/notes/:noteId`

Удаление выполняется с условием `{ id: noteId, userId }`. Успешный ответ — `204 No Content`, без тела.

Ошибки: `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `404 NOTE_NOT_FOUND` для отсутствующей или чужой заметки.

## Метод изменения заметки

Метод находится в `src/notes/notes.service.ts`. Существенная часть запроса:

```ts
return await this.prisma.note.update({
  where: { id: noteId, userId },
  data,
});
```

Начиная с Prisma 5, уникальное поле `id` можно дополнять неуникальным условием `userId` в `WhereUniqueInput`. В результате проверка владельца и изменение выполняются одним SQL `UPDATE`, без промежутка между `find` и `update`. Prisma-ошибка `P2025` преобразуется в одну прикладную ошибку `NoteNotFoundError`; HTTP-адаптер отображает ее в `404`.

## Ответы на вопросы

### Где проверять владельца

Правило «пользователь работает только со своими заметками» должно быть инвариантом сервисного слоя: оно действует независимо от того, вызван сценарий HTTP-контроллером, очередью или другим адаптером. Репозиторий или Prisma-запрос технически применяет ограничение `userId`. Контроллер только берет доверенный `userId` из контекста авторизации и валидирует формат входа; одной проверки в контроллере недостаточно.

### Как не позволить изменить чужую заметку

Нельзя сначала проверить владельца, а затем обновить запись только по `id`: между запросами состояние может измениться, и такой код легко случайно обойти. Нужно включить `userId` в тот же `UPDATE`, что и `id`, как сделано в сервисе. Для особо чувствительной системы можно дополнительно включить PostgreSQL Row Level Security, но это защита второго уровня, а не замена корректному запросу приложения.

### Какой статус вернуть для чужой заметки

`404 Not Found`, такой же, как для отсутствующей заметки. `403 Forbidden` подтвердил бы клиенту, что запись с этим ID существует. Если раскрытие существования ресурса является осознанной частью продукта, допустим `403`, но для приватных заметок безопаснее единый `404`.

### Какие поля разрешить изменять

Только `title` и `content`. `id`, `userId`, `createdAt` и `updatedAt` клиент менять не может; `updatedAt` выставляет Prisma. При создании DTO следует запрещать неизвестные поля, а в сервисе — собирать `data` по белому списку, не передавать входной объект в Prisma целиком.

### Нужна ли транзакция для одного обновления

Нет: один `UPDATE` атомарен на уровне PostgreSQL. Транзакция понадобится, если вместе с заметкой должны согласованно измениться другие записи — например, квота, аудит или outbox-событие. Внешнюю публикацию в Redis/Socket.IO лучше делать после коммита либо через transactional outbox.

### Какие индексы добавить в PostgreSQL

- Первичный ключ `notes.id` уже создает уникальный B-tree индекс и обслуживает точечный поиск.
- `users.email` имеет уникальный индекс для идентичности пользователя.
- `(user_id, created_at DESC, id DESC)` обслуживает список заметок одного пользователя и keyset pagination. PostgreSQL не создает индекс на внешнем ключе автоматически, поэтому первый столбец здесь важен.
- Индекс по `updated_at` или полнотекстовый GIN-индекс стоит добавлять только при появлении соответствующей сортировки или поиска. Каждый лишний индекс замедляет запись и занимает место.

Отдельный `(id, user_id)` не нужен: `id` уже уникален, поэтому PostgreSQL сначала находит максимум одну строку по первичному ключу и проверяет владельца.

### Если у пользователя несколько миллионов заметок

Обязательны keyset pagination, жесткий `limit`, выбор только нужных колонок и составной индекс, соответствующий фильтру и сортировке. Следует проверить планы через `EXPLAIN (ANALYZE, BUFFERS)`, ввести продуктовые лимиты/архивацию и вынести большие вложения из таблицы. Партиционирование, реплики для чтения и холодное хранение добавляются по измерениям нагрузки; преждевременное партиционирование усложнит уникальность, миграции и эксплуатацию.

### Как добавить Redis

Подходит cache-aside для чтения одной заметки: ключ `note:{userId}:{noteId}`, короткий TTL и отрицательное кеширование с еще меньшим TTL. После успешного изменения или удаления ключ удаляется; кеш списков лучше либо не вводить сначала, либо версионировать ключом `notes-list-version:{userId}`, потому что инвалидировать все варианты пагинации сложно. Проверка доступа остается в приложении и в ключе присутствует `userId`; Redis не является источником истины. При сбое Redis запрос должен уйти в PostgreSQL.

### Когда пригодится Socket.IO

Для синхронизации открытой заметки между устройствами, совместного редактирования, отображения присутствия пользователей или мгновенных уведомлений об изменении. Для обычного приватного CRUD он добавит лишнюю сложность. Событие отправляется только после подтвержденной записи в БД, комнаты авторизуются, а клиент должен уметь повторно получить состояние после разрыва соединения.

### Что тестировать в первую очередь

1. Пользователь успешно меняет свою заметку, а в запрос Prisma входят одновременно `id` и его `userId`.
2. Чужая и отсутствующая заметки дают одинаковый `404`, данные не изменяются.
3. Пустой patch, пустой/слишком длинный заголовок и запрещенные поля отклоняются или игнорируются согласно границе слоя.
4. `content: null` очищает содержимое, а отсутствие `content` его не меняет.
5. Неожиданные ошибки БД не маскируются как `404`.
6. Интеграционные тесты с PostgreSQL проверяют каскадное удаление, реальные Prisma-запросы, сортировку и пагинацию; e2e-тесты — HTTP-статусы и невозможность доступа между двумя пользователями.

## Проверка решения

Требуется Node.js 20+ и pnpm.

```bash
cp .env.example .env
pnpm install
pnpm prisma:validate
pnpm prisma:generate
pnpm typecheck
pnpm test
```

Для unit-тестов запущенная база не нужна: Prisma-клиент заменен узким mock-объектом.
